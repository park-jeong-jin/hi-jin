기술 블로그를 만들 때 자주 막히는 지점이 있습니다. **설명은 문서로 쓰고 싶은데, 예제는 클릭해 보고 싶다**는 요구입니다. 스크린샷만으로는 state가 어떻게 바뀌는지 전달하기 어렵고, CodeSandbox를 매번 붙이면 글과 예제의 버전이 어긋나기 쉽습니다.

이 사이트는 그 간극을 **MDX**로 메웁니다. 마크다운으로 본문을 쓰고, 같은 파일에 React 컴포넌트를 끼워 넣어 라이브 데모를 글 안에 둡니다. 글과 예제가 한 git 히스토리를 공유합니다.

## 이 블로그의 구성

콘텐츠는 CMS가 아니라 저장소의 파일입니다.

- `content/posts/*.mdx` — 글 본문 + frontmatter
- `src/lib/posts.ts` — 파일 읽기, 메타 검증, 목록/상세 조회
- `src/app/(site)/[slug]/page.tsx` — `next-mdx-remote`로 MDX 렌더
- `src/components/mdx/components.tsx` — MDX에서 쓸 커스텀 태그 맵 (`createMdxComponents`)

빌드·배포 시점에 파일을 읽어 정적 페이지를 만들기 때문에, 글 추가 = PR 한 번이면 됩니다.

## Frontmatter 계약

각 MDX 파일 상단은 YAML frontmatter입니다. `gray-matter`로 파싱하고, 빠지거나 잘못된 값이 있으면 빌드가 실패하도록 막아 두었습니다.

```mdx
---
title: "제목"
description: "목록·OG용 한 줄 요약"
date: "2026-07-28"
tags: ["mdx", "nextjs"]
---
```

`tags`는 `src/lib/taxonomy.ts`의 `TAGS`에 있는 값만 허용합니다. 오타로 태그 페이지가 깨지는 일을 줄이려는 선택입니다. 새 태그가 필요하면 taxonomy에 먼저 추가한 뒤 글에 쓰면 됩니다.

슬러그는 **파일명**입니다. `hello-mdx.mdx` → `/hello-mdx`. URL을 바꾸려면 파일을 이름 변경(또는 리다이렉트)하면 됩니다. `about`처럼 앱 라우트와 겹치는 이름은 쓸 수 없습니다.

## 왜 MDX인가

순수 마크다운만으로도 기술 글은 쓸 수 있습니다. MDX를 쓰는 이유는 다음 세 가지에 가깝습니다.

1. **설명과 실행의 거리** — “버튼을 누르면 count가 오른다”를 글로만 쓰지 않고, 같은 단락에 `<DemoCounter />`를 둘 수 있습니다.
2. **재사용** — Callout, 데모, 차트 같은 UI를 컴포넌트로 두고 여러 글에서 같은 API로 호출합니다.
3. **버전 관리** — 예제 코드가 글과 같은 커밋에 있어, “그때 그 데모”를 추적하기 쉽습니다.

반대로 MDX가 만능은 아닙니다. 컴포넌트 트리가 커지면 글 파일이 무거워지고, 클라이언트 컴포넌트를 남발하면 번들도 커집니다. 이 블로그에서는 **데모처럼 상호작용이 필요한 부분만** `"use client"` 컴포넌트로 두고, 본문 대부분은 서버에서 마크다운으로 렌더합니다.

## 글 안에서 컴포넌트 쓰기

MDX에서는 HTML처럼 커스텀 태그를 쓸 수 있습니다. 다만 Next에서 `next-mdx-remote`를 쓸 때는 **허용 컴포넌트 맵**에 등록된 이름만 렌더됩니다.

```mdx
<Callout title="팁">
  본문 강조나 주의사항은 Callout으로 빼 두면 읽기 흐름이 끊기지 않습니다.
</Callout>

<DemoCounter />
```

등록은 `src/components/mdx/components.tsx`의 `createMdxComponents`에서 합니다.

```tsx
export function createMdxComponents(): MDXComponents {
  return {
    Callout,
    DemoCounter,
    // ...
  };
}
```

글 페이지는 `createMdxComponents(headings)`로 제목 id를 맞춥니다. 이 글처럼 데모만 쓰는 MDX는 `createMdxComponents()`로도 동일하게 동작합니다.

맵에 없는 태그는 무시되거나 오류가 납니다. “글에 붙였는데 안 보여요”의 대부분은 등록 누락입니다.

### 새 라이브 데모 추가

1. `src/components/mdx/MyDemo.tsx`에 클라이언트 컴포넌트를 작성합니다 (`"use client"`).
2. `src/components/mdx/components.tsx`에 import 후 `createMdxComponents` 반환 객체에 등록합니다.
3. MDX에서 `<MyDemo />`로 호출합니다.

데모 UI는 본문 문단 스타일과 분리된 자체 레이아웃으로 두어, 버튼·간격이 글 타이포에 끌려가지 않게 합니다.

## 렌더 파이프라인 (짧게)

상세 페이지는 대략 다음 순서로 동작합니다.

1. `getPostBySlug`가 MDX 원문을 읽고 frontmatter와 body를 분리합니다.
2. `MDXRemote`가 body를 컴파일하고 `components` 맵을 주입합니다.
3. `rehype-pretty-code`(Shiki)가 코드 블록에 하이라이트를 입힙니다.

그래서 코드 펜스는 언어를 명시하는 것이 좋습니다. ` ```tsx `처럼 쓰면 토큰 색이 먹고, 언어 없는 펜스는 평범한 모노스페이스 블록으로 떨어집니다.

```tsx
// content는 문자열, components는 허용 태그 맵
<MDXRemote source={post.content} components={components} />
```

## 글을 추가하는 체크리스트

1. `content/posts/my-topic.mdx` 생성
2. frontmatter 채우기 (`title`, `description`, `date`, `tags`)
3. 본문 작성 — 필요 시 `<Callout>` / 데모 컴포넌트
4. 새 데모라면 `mdx/` + `components/mdx/components.tsx` 등록
5. 로컬에서 `/my-topic` 확인 후 커밋

## 정리

- 글은 content/posts의 MDX 파일 하나이고, URL은 파일명입니다.
- frontmatter와 태그는 스키마로 검증합니다.
- 상호작용이 필요할 때만 클라이언트 데모 컴포넌트를 붙입니다.
- 등록되지 않은 MDX 태그는 렌더되지 않으니, 컴포넌트 맵을 글 작성 루틴에 포함하세요.

이 글 자체가 그 파이프라인 위에서 돌아가고 있습니다. 다음 글부터는 같은 형식으로 주제만 바꿔 추가하면 됩니다.
