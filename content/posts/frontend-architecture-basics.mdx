"아키텍처"라는 말을 들으면 뭔가 대단하고 어려운 이야기처럼 느껴집니다. 실제로 한두 번 읽어서는 잘 안 들어오는 개념이기도 합니다. 그런데 사실 이 글에서 하려는 이야기는 하나뿐입니다 — **한 번 정하면 나중에 바꾸기 힘든 결정들이 뭐가 있는지**, 그리고 그 결정들이 왜 중요한지. 코드 한 줄 안 나와도 이해할 수 있게, 전부 일상적인 비유로 풀어보겠습니다.

## 아키텍처라는 말이 정확히 뭘 가리키나

집을 지을 때를 생각해봅시다. 벽지 색깔이나 조명 종류는 나중에 얼마든지 바꿀 수 있습니다. 하지만 "몇 층으로 지을지", "배관이 어디로 지나갈지", "어디가 기둥이라 못 허물지"는 처음에 정해두면 나중엔 사실상 다시 짓는 것과 다름없습니다.

프론트엔드도 비슷합니다. 버튼 색깔이나 폰트를 바꾸는 건 언제든 할 수 있습니다. 하지만 "화면을 서버가 미리 만들어둘지, 브라우저가 그때그때 만들지" 같은 결정은 나중에 뒤집으려면 그 페이지를 사실상 다시 짜야 합니다. 이 글은 이렇게 나중에 바꾸기 힘든 결정 다섯 가지를 하나씩 훑습니다:

- 화면을 서버가 미리 만들어둘지, 브라우저가 그때그때 만들지 (**렌더링 전략**)
- 화면 조각(컴포넌트)과 그 안의 값(상태)을 어떻게 나눠서 관리할지 (**컴포넌트와 상태**)
- 화면이 서버의 데이터를 어떤 통로로 받아올지 (**API**)
- 내가 짠 코드 수백 개가 브라우저가 받을 수 있는 형태로 어떻게 조립되는지 (**번들러**)
- 프로젝트와 팀이 커지면 코드와 화면을 몇 개로 쪼갤지 (**모노레포·마이크로 프론트엔드**)

## 어디서 화면을 그릴까 — 렌더링 전략

브라우저에 뜨는 화면(HTML)은 누군가 "만들어야" 나타납니다. 문제는 **누가, 언제** 만드느냐입니다.

- **CSR(Client-Side Rendering)**: 브라우저가 직접 만듭니다. 식당에 비유하면, 손님(브라우저)이 재료(자바스크립트 파일)만 받아서 직접 요리해 먹는 것과 비슷합니다. 재료를 받는 데 시간이 걸리고, 요리도 손님이 해야 하니 첫 화면이 뜨기까지 좀 걸립니다.
- **SSR(Server-Side Rendering)**: 주문이 들어올 때마다 주방(서버)에서 그 자리에서 요리해서 완성된 음식을 줍니다. 매번 신선하지만, 매번 요리하는 시간이 듭니다.
- **SSG(Static Site Generation)**: 아예 장사 시작 전에 도시락을 잔뜩 만들어둡니다. 손님이 오면 만들어둔 도시락을 바로 건네줍니다. 제일 빠르지만, 재료(내용)가 자주 바뀌는 메뉴에는 안 맞습니다.
- **ISR(Incremental Static Regeneration)**: 도시락인데, 일정 시간마다 새로 만들어서 채워둡니다. 빠른 건 유지하면서 내용도 가끔 갱신됩니다.

지금 보고 계신 이 블로그도 SSG를 씁니다. 글은 자주 안 바뀌니, 빌드할 때 모든 글을 미리 HTML로 구워두고, 방문자에게는 그걸 그대로 드립니다. 그래서 글을 열 때마다 서버가 다시 뭔가를 만들 필요가 없습니다.

<Callout title="흔한 오해">
  이 블로그는 Next.js로 만들었는데, 그렇다고 "Next.js = SSR"은 아닙니다. 2016년 처음
  나온 이유가 "React 앱을 서버에서 렌더링하게 해주자"였을 뿐이고, 지금은 SSR·SSG·ISR·CSR을
  전부 지원해서 라우트마다(더 세밀하게는 컴포넌트 단위로도) 어떤 걸 쓸지 골라 씁니다. 오히려
  기본값은 "특별히 동적이어야 할 이유가 없으면 정적"에 가깝습니다. 실제로 이 블로그도 글
  상세는 SSG, 태그 필터가 있는 홈은 동적(SSR에 가까움)으로 섞여 있습니다.
</Callout>

## 앱 안에서 코드를 어떻게 나눌까 — 컴포넌트와 상태

화면 하나를 통째로 코드 한 덩어리로 짜면 금방 감당이 안 됩니다. 그래서 화면을 레고 블록처럼 작은 조각(**컴포넌트**)으로 나눠서, 그 조각들을 조립해 전체 화면을 만듭니다. 버튼, 카드, 헤더 — 전부 하나씩의 블록입니다.

여기서 또 하나 중요한 결정이 "**상태**를 어디에 둘 것인가"입니다. 상태란 "지금 이 순간의 값" — 버튼을 눌렀는지, 입력창에 뭘 썼는지 같은 것들입니다. 이걸 어디에 두느냐가 관건인데:

- **나만 아는 것(로컬 상태)**: 이 블록 하나만 알면 되는 값. 예: 이 버튼이 지금 눌린 상태인지.
- **다 같이 아는 것(전역 상태)**: 여러 블록이 같이 알아야 하는 값. 예: 지금 로그인한 사용자가 누구인지.

로컬로 충분한 걸 전역에 두면 괜히 복잡해지고, 전역으로 둬야 할 걸 로컬에 두면 블록끼리 값을 못 주고받아서 답답해집니다. 이 경계를 어디에 그을지가 "컴포넌트와 상태" 아키텍처의 핵심입니다.

## 프론트엔드는 서버와 어떻게 대화할까 — API 경계

화면(프론트엔드)과 데이터 창고(서버, 데이터베이스)는 원래 서로 다른 건물에 있다고 생각하면 편합니다. 서로 다른 건물이니, 마음대로 아무 문으로나 들어갈 수 없고, **정해진 창구**를 통해서만 이야기를 주고받습니다. 이 창구를 API라고 부릅니다.

창구를 여는 방식에도 여러 종류가 있습니다(REST, GraphQL 같은 이름을 들어보셨을 텐데, 전부 "창구를 어떤 규칙으로 운영할지"에 대한 방식일 뿐입니다). 지금 당장 이름을 외울 필요는 없고, "화면과 데이터는 원래 분리돼 있고, 정해진 통로로만 대화한다"는 그림만 기억하면 됩니다.

## 코드를 브라우저가 이해하는 모양으로 — 번들러

개발자는 코드를 수십, 수백 개의 파일로 나눠서 짭니다(위에서 말한 "컴포넌트"들이 대부분 파일 하나씩입니다). 그런데 브라우저에게 "이 폴더에 있는 파일 500개를 하나씩 다 읽어봐"라고 시키면 너무 느립니다.

그래서 **번들러(bundler)**라는 도구가 이 수백 개의 파일을 브라우저가 받기 좋은 형태(보통 하나 또는 몇 개의 파일)로 압축하고 조립해줍니다. 이사할 때 방마다 있는 물건을 하나씩 손에 들고 나르는 대신, 박스에 챙겨 담아 트럭 한 대로 옮기는 것과 비슷합니다. Webpack, Vite 같은 이름이 이 역할을 하는 도구들이고, 이 블로그가 쓰는 Next.js는 내부적으로 Turbopack이라는 번들러를 씁니다.

재미있는 건, 이 "박스에 담아 트럭으로 옮긴다"는 개념을 한 단계 더 확장한 기능도 있다는 겁니다 — 트럭 한 대(=하나의 앱)가 아니라, **서로 다른 팀이 각자 만든 트럭 여러 대가 필요할 때 서로의 짐을 실어다 쓸 수 있게** 해주는 기능입니다. 이 이야기가 다음 섹션입니다.

## 프로젝트가 커지면 생기는 질문들 — 모노레포와 마이크로 프론트엔드

프로젝트가 작을 땐 코드 폴더 하나, 배포되는 앱 하나로 충분합니다. 그런데 팀이 커지고 앱이 여러 개가 되면 두 가지 완전히 다른 질문이 생깁니다.

**질문 1: 코드를 어디에 보관할까?** — 여러 프로젝트를 저장소(레포) 하나에 다 넣어둘지(**모노레포**), 아니면 프로젝트마다 저장소를 따로 둘지(폴리레포/멀티레포)의 문제입니다. 한 가족이 한 집에 사는지, 각자 따로 사는지에 비유할 수 있습니다. 모노레포로 가면 "이 파일 하나 고쳤을 때 뭘 다시 빌드/테스트해야 하는지" 계산이 복잡해지는데, 이걸 대신 계산해주고 캐싱까지 해주는 도구가 Nx, Turborepo 같은 것들입니다.

**질문 2: 배포된 앱은 몇 조각일까?** — 여러 팀이 만든 화면들을, 사용자 눈에는 하나의 서비스처럼 보이게 합칠지(**마이크로 프론트엔드**), 아니면 하나의 거대한 앱으로 통째로 배포할지의 문제입니다. 쇼핑몰 안에 서로 다른 매장들이 각자 운영되지만, 손님에게는 "쇼핑몰 하나"로 보이는 것과 비슷합니다. 이 마이크로 프론트엔드를 구현하는 기술 중 하나가 바로 앞에서 얘기한 번들러의 확장 기능, **Module Federation**입니다.

<Callout title="헷갈리기 쉬운 지점">
이 둘은 완전히 다른 질문입니다. 코드를 한 저장소에 모아둔다고(모노레포) 화면도 자동으로 합쳐지는 게 아니고, 화면을 여러 조각으로 배포한다고(마이크로 프론트엔드) 저장소도 자동으로 나뉘는 게 아닙니다. 두 질문의 답을 각각 따로 정할 수 있습니다. 큰 회사들이 이 둘을 같이 쓰는 경우가 많다 보니 하나처럼 보일 뿐입니다.
</Callout>

이 주제는 그 자체로 글 하나 분량이라, 오늘은 "이런 질문이 있다" 정도만 소개합니다. Nx나 Module Federation을 직접 만져보는 이야기는 다음 글에서 이어가겠습니다.

## 정리

- 아키텍처는 프레임워크 선택이 아니라, 나중에 바꾸기 힘든 구조적 결정들입니다.
- 렌더링 전략(CSR/SSR/SSG/ISR)은 화면을 **누가, 언제** 만드느냐의 문제입니다.
- 컴포넌트는 화면을 나누는 단위, 상태는 그 값을 **어디까지 공유할지**의 문제입니다.
- 프론트엔드와 서버는 원래 분리돼 있고, API라는 정해진 창구로만 대화합니다.
- 번들러는 수많은 코드 파일을 브라우저가 받기 좋은 형태로 조립해주는 도구입니다.
- 프로젝트가 커지면 "코드를 어디에 보관할지(모노레포)"와 "앱을 몇 조각으로 배포할지(마이크로 프론트엔드)"라는, 서로 다른 두 질문이 생깁니다.
