이 블로그는 날씨에 따라 하늘 색과 테마가 바뀝니다. 그런데 헤더에서 테마를 수동으로 바꾸고 새로고침하면, 아주 잠깐이지만 원래 테마가 보였다가 바뀐 테마로 바뀌는 깜빡임이 생길 수 있는 구조입니다. 이 글은 이 문제가 왜 생기고, 이 블로그는 어떻게 막았는지, 그리고 그 해결책에 아직 남아있는 허점은 뭔지를 실제 코드로 정리합니다.

## 서버 렌더링과 하이드레이션이란

이 블로그 같은 Next.js 앱은 화면을 두 번 만듭니다.

1. **서버가 먼저 완성된 HTML을 만들어서** 브라우저에 보냅니다. 그래서 페이지를 열자마자 글자와 레이아웃이 바로 보입니다.
2. 브라우저는 그 HTML을 받아 화면에 띄운 다음, **React를 그 위에 다시 한번 붙입니다.** 이 단계를 하이드레이션(hydration)이라고 부릅니다. 버튼을 눌렀을 때 반응하게 만들고, `useState` 같은 걸 실제로 동작시키는 게 이 단계입니다.

물을 스며들게 한다는 이름처럼, 이미 존재하는(서버가 만든) HTML에 React라는 "생명"을 나중에 불어넣는 과정이라고 보면 됩니다. React 공식 문서도 이 과정을 [`hydrateRoot`](https://react.dev/reference/react-dom/client/hydrateRoot)로 설명합니다.

## 하이드레이션 미스매치가 왜 생기나

문제는 2단계에서 React가 "내가 지금 만들면 이런 HTML이 나와야 하는데?"라고 검산을 한다는 겁니다. 서버가 준 HTML과 React가 브라우저에서 계산한 결과가 다르면 경고가 뜨고, 최악의 경우 화면이 순간적으로 바뀌어 보입니다.

이 차이는 서버가 절대 알 수 없는 값을 화면에 쓸 때 생깁니다. 대표적으로:

- 브라우저에만 있는 `localStorage`, `window` 값
- 접속한 사람의 시간대, 현재 시각
- 사용자가 예전에 로컬에 저장해둔 설정

서버는 이런 값 없이 HTML을 만들고, 브라우저는 이 값들을 알고 있는 채로 다시 계산하니 둘이 어긋나는 겁니다.

## 이 블로그의 실제 상황

`layout.tsx`를 보면 서버가 날씨 API로 테마를 미리 계산해서 내려줍니다.

```tsx
const weather = (await getWeather()) ?? getFallbackWeather();
const theme = resolveSiteTheme(weather.weather, weather.isDay);
const precip = resolvePrecip(weather.weather);
```

그런데 사용자가 헤더의 테마 메뉴로 "수동으로" 테마를 바꾸면, 그 선택은 `localStorage`에만 저장됩니다(`src/lib/weather/storage.ts`). 서버는 이 값을 절대 모릅니다. 그러니 사용자가 새로고침하면:

1. 서버는 (수동 설정을 모른 채) 날씨 기준 테마로 HTML을 만들어 보냅니다.
2. 브라우저는 화면에 그 HTML을 그대로 띄웁니다 — 여기서 잠깐 "원래 테마"가 보입니다.
3. React가 하이드레이션하면서 `localStorage`를 읽어 "아, 사용자가 수동으로 다른 테마를 골랐구나"를 알게 되고 테마를 바꿉니다.

2번과 3번 사이의 짧은 순간, 화면이 한 번 깜빡입니다. 스타일이 아니라 테마 값이 잠깐 틀린 경우지만, 편의상 FOUC(Flash Of Unstyled Content)라고 부르겠습니다.

## 해결 트릭 — 그리기 전에 미리 발라두기

이 문제의 핵심은 "React가 하이드레이션할 때까지 기다려야 값을 알 수 있다"는 겁니다. 그렇다면 React를 기다리지 않고 더 일찍 값을 적용하면 됩니다. `layout.tsx`는 `<head>`에 동기 스크립트를 하나 심어둡니다.

```tsx
<head>
  {/* 첫 페인트 전 수동 테마 적용 */}
  <script dangerouslySetInnerHTML={{ __html: WEATHER_BOOT_SCRIPT }} />
</head>
```

핵심 로직만 풀어서 보면 이렇습니다 (실제 소스인 `src/lib/weather/storage.ts`에는 한 줄로 압축된 템플릿 문자열로 들어있습니다).

```js
(function () {
  try {
    var d = document.documentElement;
    var o = localStorage.getItem("weather-override");
    if (!o) return;
    var p = JSON.parse(o);
    if (p.theme) d.dataset.theme = p.theme;
    if (p.precip != null) d.dataset.precip = p.precip;
  } catch (e) {}
})();
```

`<head>` 안의 일반 `<script>`는 브라우저가 HTML을 파싱하는 도중, 화면을 그리기(paint) 전에 곧바로 실행됩니다. React가 등장하기도 전에 `<html>` 태그의 `data-theme`, `data-precip` 속성을 먼저 고쳐놓는 겁니다. 그래서 사용자 눈에는 처음부터 수동으로 고른 테마만 보이고, "원래 테마 → 바뀐 테마"로 바뀌는 순간 자체가 없습니다.

## `suppressHydrationWarning`이 하는 일

boot script가 `<html>`의 속성을 미리 바꿔버렸으니, 이제 서버가 렌더링 시점에 넣은 값과 실제 DOM의 값이 다를 수 있습니다. React가 하이드레이션하면서 이 차이를 보면 "미스매치다!"라고 경고를 띄우는데, 이건 우리가 의도적으로 만든 차이이니 경고가 필요 없습니다. 그래서 `layout.tsx`의 `<html>` 태그에 `suppressHydrationWarning`을 붙여둔 겁니다.

```tsx
<html lang="ko" data-theme={theme} data-precip={precip} suppressHydrationWarning>
```

이 옵션은 [공식 문서](https://react.dev/reference/react-dom/client/hydrateRoot)에 나오듯 딱 **그 엘리먼트 한 겹**에만 적용됩니다. `<html>`에 붙였다고 그 자식들까지 전부 미스매치 검사가 꺼지는 게 아니라서, 정말 값이 달라질 수 있는 최소 범위(`<html>`의 속성)에만 정확히 걸어둔 겁니다.

## 이 프로젝트만의 방법이 아니다

이 패턴("head에 동기 스크립트로 먼저 적용 + suppressHydrationWarning")은 Next.js가 [공식 가이드](https://nextjs.org/docs/app/guides/preventing-flash-before-hydration)로 문서화해둔 방법이고, 다크모드 라이브러리로 널리 쓰이는 [next-themes](https://github.com/pacocoursey/next-themes)도 내부적으로 똑같은 방식(스크립트를 미리 주입해 `<html>`의 `data-theme`를 먼저 세팅)을 씁니다. 이 블로그의 날씨 override도 결국 "다크모드"의 변형일 뿐이라, 같은 트릭이 그대로 통합니다.

<Callout title="왜 스크립트가 이렇게 짧고 못생겼나">
  boot script는 일부러 변수명을 `d`, `o`, `p`로 줄이고 로직도 최소한만 넣었습니다. 이 스크립트는
  브라우저가 화면을 그리기 전, HTML 파싱을 멈추고 실행하는 코드라서 무거우면 그만큼 첫 화면이
  늦게 뜹니다. try/catch로 감싸둔 것도 마찬가지 이유 — 여기서 에러가 나서 파싱이 막히면 안 되니,
  실패하면 그냥 조용히 넘어가게 했습니다.
</Callout>

## 적용하며 남은 문제들

boot script로 깜빡임은 막았지만, 코드를 다시 들여다보면 아직 정리 안 된 부분들이 있습니다.

**DOM에 두 번 쓴다.** boot script가 하이드레이션 전에 `data-theme`를 먼저 쓰고, `WeatherProvider`의 `useEffect`도 마운트된 뒤 같은 속성을 또 씁니다.

```tsx
useEffect(() => {
  document.documentElement.dataset.theme = theme;
  document.documentElement.dataset.precip = precip;
}, [theme, precip]);
```

이건 버그라기보단 구조상 어쩔 수 없는 중복입니다. boot script는 첫 페인트 한 번만 처리하고 끝이라, 이후 사용자가 테마를 다시 바꾸는 건 React 쪽(`useEffect`)이 맡아야 하기 때문입니다.

**boot script는 값을 검증하지 않는다.** React 쪽 코드(`parseOverride`)는 `localStorage`에서 읽은 값이 정말 유효한 테마인지 확인하고 아니면 버립니다.

```ts
function parseOverride(raw: string | null): WeatherOverride | null {
  if (!raw) return null;
  try {
    const parsed = JSON.parse(raw) as Partial<StoredOverride>;
    if (typeof parsed?.isDay !== "boolean") return null;
    if (!isWeatherKind(parsed?.weather)) return null;
    return { isDay: parsed.isDay, weather: parsed.weather };
  } catch {
    return null;
  }
}
```

그런데 boot script는 `JSON.parse`만 성공하면 검증 없이 곧바로 `dataset`에 꽂아넣습니다. 개발자 도구로 `localStorage` 값을 이상하게 바꿔놓으면, 화면이 깨지지는 않아도(어차피 CSS에서 모르는 `data-theme` 값은 그냥 무시됨) 신뢰할 수 있는 값이라는 보장은 없는 상태입니다. boot script는 짧아야 해서 검증 로직을 그대로 옮기기는 부담스럽고, 아직은 "심각하진 않지만 정직하지 못한" 상태로 남아있습니다.

**개발 서버에서는 완전히 안전하지 않습니다.** 이 트릭은 "React가 하이드레이션할 때 DOM에 이미 적용된 값을 그대로 인정한다"는 전제로 동작하는데, [Next.js 공식 가이드](https://nextjs.org/docs/app/guides/preventing-flash-before-hydration)에 따르면 개발 모드의 React Strict Mode는 마운트 시 컴포넌트를 한 번 더 리마운트하면서 `<html>`, `<head>`, `<body>`에서 JSX가 관리하지 않는 속성을 초기화합니다. boot script가 미리 발라둔 `data-theme`/`data-precip`도 개발 서버에서는 이 리마운트 때 잠깐 지워졌다 다시 그려질 수 있다는 뜻입니다. 공식 가이드는 이런 경우를 대비해 값을 `useLayoutEffect`로 다시 적용해두라고 권장하는데, `WeatherProvider`는 지금 `useEffect`를 씁니다. 프로덕션 빌드에서는 문제가 없지만, 로컬 개발 환경에는 아주 짧은 깜빡임이 남아있을 수 있는 지점입니다.

## 정리

- 서버가 만든 HTML 위에 React가 나중에 이벤트를 붙이는 과정이 하이드레이션입니다.
- 서버가 모르는 값(로컬 설정 등)을 화면에 쓰면 서버 HTML과 클라이언트 계산 결과가 어긋나는 하이드레이션 미스매치, 나아가 화면 깜빡임(FOUC)이 생길 수 있습니다.
- 해결책은 React를 기다리지 않고, `<head>`의 동기 스크립트로 화면을 그리기 전에 값을 먼저 적용하는 것입니다. 이건 이 블로그만의 방법이 아니라 Next.js 공식 가이드와 next-themes 같은 라이브러리가 쓰는 표준 패턴입니다.
- `suppressHydrationWarning`은 "이 한 겹은 의도적으로 다르다"고 React에게 알려주는 것일 뿐, 하위 전체의 미스매치 검사를 끄는 게 아닙니다.
- 트릭 하나로 깜빡임은 막았지만, 이중 쓰기·boot script의 검증 부재·개발 서버에서의 리마운트 여지처럼 구조상 남아있는 트레이드오프도 있습니다.
