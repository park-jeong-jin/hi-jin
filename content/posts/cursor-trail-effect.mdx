이 블로그는 마우스를 움직이면 지나간 자리에 💩 이모지가 남았다가 사라집니다. 있어도 그만 없어도 그만인 이펙트지만, 막상 만들어보면 "이거 성능은 괜찮나", "다들 원하는 효과인가" 같은 질문이 따라옵니다. `CursorTrail.tsx` 하나에 담긴 그 판단들을 정리합니다.

## 제약 조건 정리

이펙트를 넣기 전에 먼저 지키고 싶었던 선이 있었습니다.

- **첫 화면 렌더링을 늦추면 안 된다.** 재미로 넣은 기능이 페이지 로딩을 느리게 만들면 본말전도입니다.
- **원치 않는 사람은 안 보여야 한다.** 움직임에 민감한 사용자, 터치 기기 사용자에게는 의미가 없거나 오히려 방해입니다.
- **마우스를 빠르게 움직여도 버벅이면 안 된다.** `pointermove`는 프레임마다 여러 번 발생할 수 있는 이벤트입니다.

아래 내용은 이 세 가지를 어떻게 지켰는지에 대한 기록입니다.

## 첫 렌더를 막지 않기

`CursorTrail`은 `useIdleReady`라는 훅으로 감싸져 있고, 이 훅이 `true`를 반환하기 전까지는 아무것도 렌더하지 않습니다.

```tsx
// src/hooks/useIdleReady.ts
const IDLE_TIMEOUT_MS = 1500;
const FALLBACK_DELAY_MS = 200;

export function useIdleReady() {
  const [ready, setReady] = useState(false);

  useEffect(() => {
    const show = () => setReady(true);

    if (typeof window.requestIdleCallback === "function") {
      window.requestIdleCallback(show, { timeout: IDLE_TIMEOUT_MS });
    } else {
      window.setTimeout(show, FALLBACK_DELAY_MS);
    }
  }, []);

  return ready;
}
```

`requestIdleCallback`은 브라우저가 한가할 때 콜백을 실행해달라고 예약하는 API입니다. 첫 페인트, 폰트 로딩, 다른 컴포넌트의 hydration 같은 더 중요한 작업이 끝난 뒤에야 커서 트레일이 붙습니다. Safari처럼 이 API가 없는 브라우저를 위해 `setTimeout` 폴백도 같이 둡니다.

<Callout title="timeout 옵션이 있는 이유">
  `requestIdleCallback`은 브라우저가 계속 바쁘면 콜백을 무한정 미룰 수 있습니다. `timeout: 1500`은
  "아무리 바빠도 1.5초 안에는 실행해달라"는 마지노선입니다.
</Callout>

## 끄고 싶은 사람은 끄게

`ready`가 되어도 곧바로 이벤트를 붙이지는 않습니다. 두 가지 조건을 먼저 확인합니다.

```tsx
if (window.matchMedia("(prefers-reduced-motion: reduce)").matches) return;
if (!window.matchMedia("(pointer: fine)").matches) return;
```

`prefers-reduced-motion`은 OS 설정에서 "동작 줄이기"를 켠 사용자를 위한 미디어 쿼리입니다. `pointer: fine`은 마우스처럼 정밀한 포인터 장치가 있는지를 봅니다. 터치 기기에서는 애초에 "커서가 지나간 자리"라는 개념이 없으니 이벤트 리스너 자체를 등록하지 않습니다.

이 두 체크는 마운트 시점에 한 번만 확인합니다. 그런데 터치스크린이 달린 노트북처럼 마우스와 터치를 함께 쓰는 하이브리드 기기에서는, 주 입력장치가 마우스라 `pointer: fine`은 여전히 참인 채로 개별 터치 이벤트도 `pointermove`로 들어올 수 있습니다. 그래서 `onMove` 안에서 이벤트 하나하나를 한 번 더 거릅니다.

```tsx
function onMove(e: PointerEvent) {
  if (e.pointerType !== "mouse" || !container) return;
  // ...
}
```

## 마우스무브를 얼마나 자주 처리할까

`pointermove`를 그대로 받으면 마우스를 조금만 움직여도 이모지가 촘촘하게 찍혀 지저분해집니다. 보통은 `setTimeout`이나 `requestAnimationFrame`으로 "몇 ms마다 한 번만" 처리하는 시간 기반 스로틀링을 쓰는데, 여기서는 거리 기반으로 걸러냅니다.

```tsx
const MIN_DISTANCE = 28;

const last = lastPos.current;
if (last) {
  const dx = e.clientX - last.x;
  const dy = e.clientY - last.y;
  if (dx * dx + dy * dy < MIN_DISTANCE * MIN_DISTANCE) return;
}
lastPos.current = { x: e.clientX, y: e.clientY };
```

시간 기준으로 거르면 마우스를 가만히 떨고만 있어도, 혹은 아주 천천히 움직여도 일정 간격마다 이모지가 찍힙니다. 거리 기준으로 거르면 "실제로 28px 이상 움직였을 때만" 찍히기 때문에, 트레일 간격이 마우스 속도와 무관하게 항상 일정합니다. `Math.sqrt` 없이 거리의 제곱끼리 비교하는 것도 매 이벤트마다 불리는 코드라 굳이 제곱근 연산을 넣지 않은 선택입니다.

## React state를 안 쓴 이유

이모지 하나하나를 `useState`로 관리하는 배열에 넣고 렌더하는 방식도 가능합니다. 하지만 마우스가 빠르게 움직이면 `pointermove`가 초당 수십 번씩 발생하고, 그때마다 state가 바뀌면 그만큼 리렌더가 따라옵니다. 화면에 보이기만 하면 되는 요소를 위해 React 트리 전체가 다시 계산될 이유는 없다고 판단해서, DOM을 직접 만들고 지웁니다.

```tsx
const dot = document.createElement("span");
dot.className = "cursor-trail-dot";
dot.textContent = "💩";
dot.style.left = `${e.clientX}px`;
dot.style.top = `${e.clientY}px`;
container.appendChild(dot);
```

컨테이너 자체는 `<div>` 하나뿐인 일반 React 엘리먼트이고, 그 안의 자식들만 vanilla DOM API로 직접 추가합니다. React가 모르는 자식이 생기는 셈이지만, 이 컨테이너의 자식을 React 쪽에서 다시 읽거나 렌더링에 관여시키지 않기 때문에 문제가 되지 않습니다.

## 파티클 정리 로직

찍힌 이모지는 CSS 애니메이션으로 사라집니다 (`cursor-trail-fade`, 700ms). 문제는 "다 사라진 다음 DOM에서도 지워야 한다"는 뒷정리인데, 애니메이션 종료 이벤트 하나에만 의존하지 않습니다.

```tsx
const FALLBACK_CLEANUP_MS = 1200;

const cleanup = () => dot.remove();
const fallbackId = window.setTimeout(cleanup, FALLBACK_CLEANUP_MS);
dot.addEventListener(
  "animationend",
  () => {
    window.clearTimeout(fallbackId);
    cleanup();
  },
  { once: true },
);
```

`animationend`는 대부분의 경우 정확히 700ms 뒤에 발생하지만, 아예 오지 않는 경우가 있습니다. `prefers-reduced-motion` 체크는 마운트 시점에 딱 한 번만 하는데, `weather.css`의 `@media (prefers-reduced-motion: reduce)`는 페이지가 떠 있는 동안 계속 살아있는 미디어 쿼리입니다. 그래서 페이지를 연 채로 OS의 "동작 줄이기" 설정을 나중에 켜면, JS 쪽 가드는 이미 지나간 뒤라 이모지는 계속 생성되는데, CSS에서 `.cursor-trail-dot`에 `animation: none`이 걸려버려 `animationend`가 영원히 발생하지 않는 상황이 생깁니다. `animationend`가 오지 않아도 1.2초 뒤에는 무조건 지우는 `setTimeout`을 같이 걸어두면, 이런 경우에도 이모지가 화면에 계속 남아 쌓이는 일은 없습니다.

또한 `MAX_PARTICLES`(24개)로 동시에 떠 있을 수 있는 이모지 개수 자체도 제한해서, 정리 타이밍이 아무리 어긋나도 DOM 노드가 무한정 늘어나지는 않게 이중으로 막아둡니다.

## 정리

- `requestIdleCallback`으로 첫 페인트 이후로 이펙트 등록을 미룹니다.
- `prefers-reduced-motion`, `pointer: fine`으로 원치 않거나 의미 없는 환경에서는 아예 켜지지 않게 합니다.
- `pointermove`는 시간이 아니라 거리 기준으로 걸러, 마우스 속도와 무관하게 트레일 간격을 일정하게 유지합니다.
- 리렌더 비용을 피하려고 트레일 파티클은 React state가 아니라 DOM을 직접 조작해 추가·제거합니다.
- 파티클 정리는 `animationend` 하나만 믿지 않고, fallback `setTimeout` + 최대 개수 제한으로 이중 안전장치를 둡니다.
